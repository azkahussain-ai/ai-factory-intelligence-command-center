# Synthetic Data — Source & Assumptions

**All data in `data/raw/` and `data/processed/` for this project is synthetic.**
No real factory, sensor, or maintenance data was collected. This document
states exactly what was generated, how, and why, so downstream users of the
data do not mistake it for real-world observations.

## What is synthetic

- `raw_sensor_data.csv` — 15-minute sensor readings for a 6-machine fleet.
- `raw_production_data.csv` — shift-level production/quality records.
- `raw_maintenance_data.csv` — maintenance/incident notes.

## Why synthetic

A network-accessible copy of a real manufacturing sensor stream at this
scale, licensed for reuse, was not available in this environment. The
**AI4I 2020 Predictive Maintenance Dataset** (UCI Machine Learning
Repository, Matzka 2020) was used as the *methodological* reference instead
of downloading it, because the UCI archive itself states plainly: *"The AI4I
2020 Predictive Maintenance Dataset is a synthetic dataset that reflects
real predictive maintenance data encountered in industry"* — i.e. it is not
real collected sensor data either. We replicated its documented generation
process (temperature as a normalized random walk around 300K, torque drawn
from N(40, 10) Nm, rotational speed derived from a fixed rated power divided
by torque) rather than fabricate an unrelated distribution.

Vibration and pressure channels are not part of AI4I and have no equivalent
public grounding at this scope; their baselines (`config/config.py:
MACHINE_TYPE_PROFILES`) were chosen to be plausible for the stated machine
class (CNC / Press / Injection Molder) and are explicitly a modeling
assumption, not a measured value.

## Generation assumptions

- **Machine count:** 6 (`M-01`…`M-06`), 2 each of CNC, Press, Injection_Molder.
- **Quality variant mix:** follows AI4I's documented L/M/H proportions (50/30/20%) at the fleet level.
- **Time range:** 90 simulated days starting `2026-05-01`.
- **Sampling frequency:** sensors every 15 minutes; production aggregated per 8-hour shift (Morning/Afternoon/Night); maintenance notes at irregular, event-driven timestamps.
- **Random seed:** `42` everywhere randomness is used (`config.RANDOM_STATE`), so regenerating the pipeline reproduces identical data.
- **Degradation/failure logic:** each machine is independently assigned 0–3 "degrade-to-failure" episodes. Each episode ramps vibration/temperature/pressure upward over a random 3–7 day window, culminating in a failure event, followed by 2–24 hours of downtime (sensors offline, `operating_status = DOWN`) before returning to baseline. This is a documented rule-based simulation, not sampled from any real failure log.
- **Production impact:** production rate and quality score degrade proportionally to the same ramp factor used for sensors, so the tabular and time-series views are internally consistent for later multimodal integration.
- **Maintenance notes:** one corrective note per failure episode (templated text referencing the affected machine and a plausible symptom) plus 3–7 routine preventive entries per machine, generated independently of the ML/DL pipeline so NLP work in a later stage has genuine (if templated) text to parse.

## Deliberately injected data-quality issues

To give Stage I's cleaning code real problems to solve, the **raw** files
(not the cleaned outputs) contain:

- Sensor dropout: ~0.4% of numeric sensor readings randomly set to missing, independent of the legitimate "sensors offline during downtime" missingness.
- ~20 physically impossible sensor glitches (negative vibration/pressure, negative Kelvin temperature, a 999999 rpm reading).
- Inconsistent categorical labels (`"CNC"` vs `"cnc"`, `"RUNNING"` vs `"running"` vs `"Running"`).
- 10–15 exact duplicate rows in the sensor and production tables.
- 6 malformed timestamp strings (`"unknown"`) in the sensor table.
- A handful of impossible `production_count` values (`-1`).
- ~8% of maintenance `urgency` values missing (reflecting that real incident logs are often filled in inconsistently).

These are all fixed or documented (never silently dropped without reason) in
`src/preprocessing/clean_data.py`.

## Limitations

- Sensor channels beyond temperature/torque/rotational speed (vibration, pressure) follow assumed, not empirically measured, distributions.
- Failure episodes are independent across machines; no fleet-wide correlated failure modes (e.g. shared power-supply events) are modeled.
- Maintenance note text is templated, not natural free text from real technicians, which will cap the realism of later NLP work.
- Downstream model performance on this data should not be assumed to transfer to a real factory.

## Stage III addition - synthetic equipment images

`data/synthetic/images/` (100 images, `images_metadata.csv`) is also
synthetic, generated by `src/computer_vision/generate_synthetic_images.py`
because **no real equipment/product images existed anywhere in the
project** at the start of Stage III. Each 32x32 grayscale image is a
rendered circular "component" against noisy background; "defect" images add
a scratch or dark pit mark, "normal" images do not. Images are tagged with
a `machine_id` from the existing 6-machine fleet via simple round-robin
assignment - this pairing is for later multimodal joins in the structured
output and is not a real inspection-to-machine mapping. Generated with
`RANDOM_STATE=42`, split 60/20/20 (train/validation/test), stratified by
label.
